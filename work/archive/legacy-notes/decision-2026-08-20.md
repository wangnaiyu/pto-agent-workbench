# decision-2026-08-20

## 移除“双 Agent 协作分工”限制

> 本分区 `owner: DeepSeek`、`source: user`、`status: accepted`、`decision: accepted`。

### 背景

工程骨架沿用了 PyPTOUX 的"双 Agent 协作分工"约定：

- AGENTS.md §2「角色分工」：Codex → host 插件 / 构建 / 装配 / rebase；Claude → client UI / 工作台视觉；官方 DSH → dogfooding 动态插件验证。
- docs/rules.md R7「分工」：同上的角色映射。
- references/PyPTOUX.md：「双 Agent 分工沿用：Codex（规划/事实/构建/Git）、Claude（前端/视觉/交互）」。

### 决策

本工程内不再按"双 Agent 协作分工"执行，移除该限制：

- AGENTS.md §2 改为「多 agent 协同（暂不预设）」，不设固定角色分工。
- docs/rules.md 删除 R7「分工」，R8–R14 顺延为 R7–R13。
- references/PyPTOUX.md 删除「双 Agent 分工沿用」条目（PyPTOUX 自身的约定仍可作为其内容参考，但不约束本工程）。

### 理由

双 Agent 分工是 PyPTOUX（内容与知识库项目）的内部约定，直接套用到本工程（DSH 改造工程）没有实际运行验证；真实的协同需求要等工作台工作流实际跑起来才知道。先去掉硬性限制，避免预设角色束缚实际协作方式。

### 影响

- 单 writer / 交接纪律（现 R6）不受影响，继续有效。
- 只移除"角色分工"限制；接手流程（现 R7）、改造优先级（R1）、数据规则（R8/R9）、发布（R10/R11）、记录（R12/R13）等其余规则不变。

### 后续

待工作流实际跑通一段时间后，复盘真实多 agent 协同模式，再沉淀正式规则（回填本记录或另立新 decision）。

## PTO Agent 工作台改用预构建发行包

> 本分区 `owner: Codex`、`source: user`、`status: accepted`、`decision: accepted`。

### 决策

普通用户的正式安装与启动接口改为与官方 DSH 同类的单条 `npx` 命令。发布包携带在 CI 中生成的 platform-specific 生产运行时，用户机器仅要求 Node.js/npm，不要求 Git、SSH、pnpm、Corepack、源码 checkout 或本地全量构建。

源码搭建仅作为开发者流程，从主 README 的普通用户快速开始中移出；不再维护一份与自动脚本重复的“手工快速开始”。

### 理由

- 从用户路径上直接移除 SSH clone、Git HTTP 超时、pnpm/Corepack 缺失和本地构建差异。
- launcher 从自身安装位置定位运行时，并把持久数据存入 `~/.dsh-pto-workbench/`，不依赖 checkout 路径或调用时的当前目录。
- 薄 launcher 依赖官方 DSH 的方案虽然包小，但空 npm cache 中依赖 metadata 冷解析超过 300 秒；单一预构建运行时更符合一键安装的稳定性目标。

### 验证与发布门槛

macOS arm64 spike 已用本地 npm tarball 通过空目录端到端烟雾测试；产物约 64.8 MB，能启动并返回 PTO 品牌首页。对外发布前必须补齐 macOS / Linux / Windows 平台包、跨平台解压、升级/回滚、供应链 provenance 与离线 Release 包。

## 工作台任务起始对象与信息架构

> 本分区 `owner: Claude`、`source: user`、`status: accepted`、`decision: accepted`。

### 核心模型

工作台的任务起始对象分三层，分属三条不同的轴，不可压平为一层：

| 层 | 对象 | 角色 | 落到 DSH |
|---|---|---|---|
| 作用域 | 算子工程根目录 | 一切读写的边界 | workspace（= 目录，机制强绑定） |
| 起始点 | 一次运行（build_output 下的 run 目录） | 任务的由头与诊断对象 | 会话内的结构化 run reference |
| 载体 | agent 任务 / 会话 | 用户回来要找的东西 | DSH session |

由此得到贯穿全部决策的基本区分：**会话 cwd 是作用域，run 是会话的诊断对象参数**。二者在"独立运行记录工作区"场景下重合（上面没有更大的东西可扎根），在工程工作区场景下分离。

### 1. 侧边栏信息架构

侧边栏保留双 Tab：**会话 / 运行记录**（原"运行历史"改名，对齐 `interface-frame-workbench` 的 `运行记录ID` literal）。

- 运行记录列表与会话树**同构**：按工作区分组 + 未分组。
- **未分组承载用户显式打开的独立 run**。归属判定：canonical path 的父目录命中已注册工作区则归该工程组，否则未分组。
- 运行记录 Tab 标题栏图标组**只有搜索**；`＋`（打开运行记录）挂在**未分组组行**，hover 显现；工程组行不显示 `＋`（工程组下的 run 是扫出来的，不能手工加）。
- 无新会话图标、无视图选项、无 groupBy（脱离工程的 run 列表无意义）。
- 折叠栏（rail）不承载运行记录。
- **两棵树的未分组都常驻渲染**。会话未分组是「未归属会话桶」：汇集无 Workspace 归属的真实会话，其组行 `＋` 只在浏览器创建不含 SessionId 的 Host-cwd 草稿；标题栏“新会话”也只创建客户端草稿，目标依次继承明确／当前／最近 Workspace，再回退 Host cwd。点击和 Workspace 切换都不调用 `session.create`、不分配 SessionId、不落盘；首次发送才按“创建 → 应用前置准备 → 提交 prompt”实体化。导航隐藏所有 blank 行，首讯被接受后才在 Workspace 或未分组显示并置顶。运行记录未分组仍是「导入桶」。两者局部空态仅在本组展开且为空时显示；所有会话文件夹状态色统一表示「已展开且包含当前真实会话」。
- 数据源：按需扫盘（不常驻 watch）+ 一份用户显式打开记录的持久化清单。移除只摘登记、绝不动目录（照 `workspaceRegistry.delete` 口径）。
- 定位：运行记录列表用于**回溯与挑选**，不是任务起点。

### 2. 工作区维度与两类工作区

工程工作区**只能是算子工程根目录**，这是机制约束不是偏好：会话归属靠 cwd 精确字符串相等（`workspace/entity.ts:138`），`SessionHeader.cwd` 不可变且是 `workspace-write` 下唯一可写根。选子目录会导致 agent 写不到工程其他部分。

引导文案点名"**选择当前要编辑的算子 / 模型业务工程根目录**"，不用泛泛的"选择文件夹"。该根目录应覆盖本次任务需要修改的业务源码、配置、golden 与测试；**不再要求其中包含 `pypto` 框架 checkout，也不要求所有 run 都位于其下**。PyPTO 可以是相邻 checkout 或已安装的只读依赖，外部 run 通过结构化 reference 关联。

存在**两类工作区**，能力不同：

| | 工程工作区（工程根） | 运行记录工作区（单个 run 目录） |
|---|---|---|
| 条件 1 解读数据 / 2 面板 / 3 选区回流 | 可用 | 可用 |
| 条件 4 改码重跑 | 可用 | **不可用（无源码）** |
| 两个已有 run 对比 | 可用 | 可用 |

- 独立运行记录采用**延迟注册**：打开时只进运行记录清单，**首次在其上开会话时才 `workspaceRegistry.create()`**，避免会话 Tab 的工作区列表被看过即丢的 run 污染。
- 会话 Tab 中两类工作区靠**内容推断**渲染不同图标（`workspaceRegistry` 只存 path + title，不为此改内核，遵 R1/R6）。
- 父子工作区并存（先开独立 run、后加父工程）**不做提示**。父工程注册后，其内的 run 照常被扫出并显示在工程组下，独立 run 的卡片保留在未分组，两张卡产出的会话按各自 cwd 归属。
- **未分组卡片必须带「作用域不含源码」标记**：同一物理目录的两张卡能力不同，原因不可见，标记是消除歧义的最低成本手段。
- 允许在父工程注册后继续新建以 run 为根的会话（保留只读围栏用法）。

### 3. Happy path 起点

**当前从侧边栏运行记录起步**，这条路可以完整走通。

- **侧边栏点 run ≠ 新建会话**。run 卡片是**多操作对象**：查看某个具体产物（可视化或源码）、查看该 run 的报告看板、新建会话等；"新建会话"是卡片上一个明确入口（hover 显现或收进「更多」菜单），不是点击的默认行为。卡片操作集由后续设计确定。
- **对话初始页保持留白**，其功能待整体挖掘后再定。备选方案存档：空白页在该工作区有 run 时渲染「最近运行」（3–5 条 + 查看全部），无 run 时保持现状；选中 run 后作为 context chip 绑定并给意图建议，建议**填入输入框而不自动发送**。
- 一个会话可挂**多个 run**（cwd 不可变但诊断对象是参数），否则两次运行对比需开两个会话。
- 独立 run 工作区的会话**自动预挂**诊断对象（无选择余地）。
- run → session 反向索引（"该运行记录已有 N 个相关会话"）暂不做。
- **设计态不另造机制**：工程名含"设计"，但四个条件全部落在诊断与调优侧；设计态就是 agent + bash + fs，DSH 开箱即有。

### 4. 报告看板落点

**看板要做。v1 只实现调起路径与浮层壳，内容留空。**

机制核实决定了落点：`shell.overlay` 是**唯一在无当前会话时仍渲染的挂载面**（`ui-layout/AppFrame.tsx:193` 无条件渲染；同文件注释记明 details 是 session-strict，无会话时渲染为空）。而 run 卡片的"查看产物 / 查看看板"必须能脱离会话使用，故：

- **`shell.overlay` = 观看面**（全帧，会话有无都能开，且不打断会话）
- **`details` = 联动面**（右栏，须有会话，随主画布选中对象联动）
- 二者共用组件但**分级而非同形**：overlay 承载完整看板，details 只承载摘要（四区在可调宽右栏塞不下）

**撤回**「报告看板 = `interface-frame-workbench` 四区」的等式。四区是**泳道为主画布的性能诊断 renderer**，预设了"要看的是性能"和"入口是泳道"；而精度问题（`args_dump` / IR 差异线）不走泳道。**四区是看板的一种 renderer，不是看板的定义。**

> **对 PyPTOUX 的联动状态：已完成。** `interface-frame-workbench` 已降级为“具备 timeline 证据时的性能诊断 renderer”，不再作为通用报告看板模板；缺少 timing 时不得渲染空泳道或伪造性能视图。对应任务包已完成并归档。

v1 壳仍只承诺挂载面、一个或多个 run reference、调起方、生命周期和会话有无时的行为差异。内部内容现增加一层 **evidence gate + renderer selection**，但不等于所有 renderer 已设计完成：

| 证据 / 问题类型 | v1 处理 | 状态 |
|---|---|---|
| 有 `timeline`，任务是运行时性能诊断 | 可采用四区性能诊断 renderer | 选择规则已完成 |
| 有 `tensorValues`，任务是精度分析 | 进入精度 renderer | 具体布局待设计 |
| 有 `irLowering` / compile evidence | 进入编译过程 renderer | 具体布局待设计 |
| 证据不足或 join 不可靠 | 先显示 evidence health、缺失项与补采方法，不渲染假主画布 | 准入规则已完成 |

因此“看板内部内容与视角设计”由一项笼统待办拆成：renderer 选择契约已完成；精度、编译及通用 evidence inventory 的具体交互仍待设计。

### 5. 运行记录识别规则

以 pypto 3.0 本地镜像当前复核快照（branch `main`，commit `97e4ef8ec422357c40ef54b1499511ecfb5ac3fb`，2026-08-24）源码为准。旧结论保留时必须重新校验其 literal 与行号。

- **产物默认位置** `<cwd>/build_output/<program.name>_<YYYYMMDD_HHMMSS>/`（`python/pypto/ir/compile.py:316-322`）。三层覆盖：`output_dir` 参数 > `PYPTO_PROG_BUILD_DIR` 环境变量 > `build_output`。**相对运行时 cwd，不是工程根。**
- **`_jit_` 前缀不可用于识别**：它来自 JIT 装饰器（`python/pypto/jit/decorator.py:2346` `class_name = f"_jit_{self.__name__}"`），只在 `@pl.jit` 路径出现；手写 pypto 源码 + `ir.compile()` 的 program name 无此前缀。仅在采用默认命名时，目录名才通常带尾部 `_%Y%m%d_%H%M%S`；显式 `output_dir` 可以是任意名称。
- **采用 pypto 自身的判定**（`python/pypto/runtime/debug/replay.py:159-169`，源码中唯一显式的 build_output 目录判定）：
  - L2 单芯片：顶层存在 `kernel_config.py`
  - L3 分布式：顶层无 `kernel_config.py`，但存在 `orchestration/host_orch.py`（各 L2 子程序在 `next_levels/<program>/`；rank / device 是 runtime DFX identity，不是该目录名的语义）
  - 两者皆无 → 拒绝，并复用其错误语义作为"打开运行记录"的拒绝理由
- **嵌套不作为独立条目**：`next_levels/<program>/` 下是 L2 子构建，作为父 run 的下级呈现；否则一个 L3 run 会在列表中炸成 N 条。rank / device 从 `dfx_outputs/` 等 runtime evidence 解析，不从 `next_levels/` 目录名猜测。
- **metadata sidecar 是能力探测而非识别条件**：L2 的 `compiled_meta.json` 可支持 `CompiledProgram.from_dir`；L3 使用 `distributed_meta.json` 表达分布式 compiled identity。缺失 metadata 时仍可能是合法历史 capture，但复跑能力应降级为 `debug/run.py` 或完整重编译，不能把 metadata 缺失写成“不是运行记录”。
- **路径不可依赖**：工程根目录名由用户自定（多为"模型+算子"），`build_output/<name>_<ts>` 的 `<name>` 来自用户函数名。整条路径无一片段承载识别语义，识别一律靠内容。
- **不让用户配置扫描路径**：用上述内容判定做**有限深度递归**，剪枝跳过 `.git/`、`node_modules/`、`__pycache__/`、`3rdparty/`；**认出 run 目录即不再下探**（例外：`next_levels/` 下探一层）；按需扫、不 watch。此法天然覆盖 `build_output/`、子目录中的 `build_output/` 以及被 `output_dir=` / `PYPTO_PROG_BUILD_DIR` 改到任意位置的产物。

### 6. 算子工程目录结构（2026-08-24 更新）

后续对 `pypto`、`pypto-lib`、运行 capture、`PTO-TestData` 与 `ops-transformer` 的复核，纠正了初版把“完整依赖拓扑”当成“普通用户工程目录”的问题。

#### 6.1 旧结论状态

| 初版结论 | 当前状态 | 更新后的结论 |
|---|---|---|
| 默认采用“框架与业务算子同仓”的拓扑 1 | **superseded** | 普通业务用户默认打开独立业务工程；框架通常是相邻 checkout 或安装的只读依赖 |
| `build_output` 严格追加、从不覆盖 | **superseded** | 默认时间戳通常支持多 run 并存，但 `exist_ok=True`、显式复用 `output_dir` 或同秒同名可能写入已有目录 |
| 尚未取得 `pypto-lib` | **completed** | 已建立本地只读镜像并验证 model-build、golden、contract、weights、extern kernel 与 serving 结构 |
| 在实验工程根放 `EXPERIMENT.md` 保存内部来源说明 | **superseded** | 工作台 / PyPTOUX 内部治理元数据必须放在用户项目之外，不向用户工程注入专用文件 |
| A 框架 → B 业务实现 → C 运行证据 | **accepted / expanded** | 继续成立，但要分别表达 dependency topology、user project 与 run evidence 三种视图 |

#### 6.2 三种目录视图

**依赖拓扑**用于 Agent 和环境诊断，不等于用户日常工程：

```text
<work-root>/
├── pypto-3.0/                  # 框架 / DSL / IR / Pass / CodeGen / runtime API；通常只读
├── pypto-lib/                  # 一种真实业务实现仓；普通用户也可能使用自己的独立仓库
└── ptoas-bin/                  # 外部 toolchain；版本由框架 pin 约束
```

**用户工程**只显示用户实际拥有、编辑或交付的源码、配置、验证和运行结果，不复制完整框架依赖：

```text
<business-project>/
├── README.md
├── config / entry / kernels   # 真实 literal 按原项目保留，不强制统一命名
├── golden / tests             # 按角色可选
└── build_output/              # 仅当本工程 cwd / output_dir 实际落在这里时存在
```

**运行证据**是一个或多个可独立打开的 run reference。它可以位于业务工程内、model-build 子目录、外部 output root，或作为单独 evidence pack 被接收；source / run 关系必须显式记录，不能从父子路径猜测。

#### 6.3 用户角色 Archetype

角色化目录已经独立沉淀，不再附属于 `pypto-lib`：

| ID | 角色 / 作业 | 对工作台的含义 | 状态 |
|---|---|---|---|
| A1 | 学习者 / 单 kernel | 最小入口、输入 / golden、一次 compile 或 validation run | 已定义 |
| A2 | 业务算子开发者 | 多文件源码、配置、测试、baseline / diagnostic runs | 已定义 |
| A3 | model-build / serving 集成 | 多 entry、weights、contract、变体、extern kernel | 已定义 |
| A4 | 分布式模型开发 | topology、L3 program / dispatch / rank identity | 已定义，真实 fixture 待补 |
| A5 | 精度 / 性能调优作业 | 同一工程上的 baseline、diagnostic、candidate、verification | 已定义 |
| A6 | run-only evidence 接收者 | 无源码时能力降级，不补造假源码 | 已定义 |
| A7 | Ascend C 标准算子 / 迁移开发 | 邻近生态与迁移源工程，不定义 PyPTO 必备目录 | 已定义 |

`ops-transformer` 主体是 Ascend C 算子工程；其中仅 3 个已检视 kernel 使用 `pypto_pro` 混合构建。按用户确认，`pypto_pro` 属于 GitCode PyPTO 2.0 的继续演进线，与 PyPTO 3.0 分开，不能用这些样本推导 3.0 canonical fixture。

#### 6.4 Workspace 选择

- **普通业务开发默认**：选择能覆盖本次可编辑业务源码、共享 harness 与测试的最小完整仓库根；例如独立算子仓或完整 `pypto-lib` checkout。不要因为单个 model-build 位于子目录就把 workspace 缩到无法访问共享 `golden/`、`contract/` 和 tests 的叶子目录。
- **框架贡献任务**：需要修改 PyPTO 编译器时，另以 `pypto-3.0` checkout 作为工程 workspace；不要默认给普通算子任务框架写权限。
- **run-only 任务**：保持独立运行记录工作区，明确“作用域不含源码”，只提供证据解读、已有 run 比较和受限复跑能力。

#### 6.5 Run identity 与覆盖防护

默认目录名 `<program.name>_<timestamp>` 只适合展示与排序。一次可比较、可复现运行至少需要组合：业务源码 revision / dirty state、PyPTO / simpler / PTOAS / PTO ISA revision、entrypoint、compile / runtime config、输入与权重 identity、CANN / platform / hardware、DFX 配置。

- `ProjectRef`、`RunRef` 与 `sourceJoin`（`exact | candidate | unverifiable-missing`）进入工作台对象模型；
- baseline / diagnostic / candidate / verification 角色必须显式记录，不能按时间先后推断；
- before / after 只有在 task identity 与 metric identity 同口径时成立；
- 扫描、重跑和实验工具在写入已有 output dir 前必须提示或建立新目录，不能假设上游永不覆盖。

#### 6.6 实验工程与内部元数据

`pypto-lib` 镜像已取得，现可从真实源码构造 A1 / A2 / A3 工程；但现有历史 capture 没有自动获得 exact source revision，因此“仓库接入”已完成，“每份 capture 的源码↔产物精确联结”仍是 fixture 级待办。

工作台不得在用户工程内创建 `.pyptoux/`、`EXPERIMENT.md`、fixture manifest 或其它项目专用标识。内部的 L1 / L2 / L3、C0–C4 completeness、source mapping、run role 与 share-safe 信息由 app-owned sidecar registry 保存，建议落在：

```text
~/.dsh-pto-workbench/
└── fixture-registry/<fixture-id>/fixture-manifest.json
```

registry 使用 `project_ref` 与 `run_refs` 关联原生项目、实验副本和运行证据；导入项目时不回写，导出 / 分享用户工程时默认排除。

### 7. 发现层接缝与对象模型

扫描与"工程内寻物"独立成层，接缝划在对象模型上：

```
发现层（会变）：recognizer 规则集 —— L2Run / L3Run / JitEntry / DfxArtifact …
        │  输入一个目录，输出结构化对象
        ▼
对象模型（要稳）
        │
        ▼
消费方（不因工程形态变化而改）：侧边栏列表 / run 卡片与操作 / 看板 /
        给 agent 的 run reference / 重跑与对比工具
```

**唯一规矩：路径只能作为 opaque locator / reference 携带，不能成为对象模型的语义 ID 或 join key。**

| 会绑死下游 | 下游安全 |
|---|---|
| `passesDumpDir: "build_output/x/passes_dump"` | `passSnapshots: [{ordinal, stageLabel, passName}, …]` |
| `hasDfxOutputs: true` | `evidenceRole: "runtime-observed"` |
| `swimlaneJsonPath: "..."` | `capabilities: { timeline: true, criticalPath: false }` |

原始路径仍随对象携带，但作为 **opaque 数据**（供 agent 实际读文件），不作为下游的 key——同时满足 R5 / P7.2「不改写上游 literal」。

稳定对象模型至少增加：`ProjectRef`、`RunRef`、`productLine`、`sourceJoin`、`runRole`、`capabilities` 与 `rerunCapabilities`。其中 `sourceJoin` 决定能否把源码和产物作语义联结，`runRole` 决定能否进入 baseline / candidate 比较；两者都不能由路径或时间戳自动升级。

**模型不自造**：直接对齐 PyPTOUX `02-knowledge/00-shared/pypto-data/schemas/compiler-pass-artifacts.md` §2 的归一化记录（`capture_id`、`pipeline_id`、`snapshot_ordinal`、`snapshot_file`（保持原始相对路径）、`stage_label`、`pass_name`、`content_sha256`、`changed_from_previous`、`diagnostics`、`derived_views`），其原话即本规矩："不同 PyPTO 版本可以保留自己的 raw 文件名和目录结构；知识库或 demo adapter 应归一到以下概念，而不是改写 raw literal。"

**recognizer 做成规则集**，每个声明：识别什么、给定目录如何判定、提取哪些语义字段。首批四个：`L2Run`（`kernel_config.py`）、`L3Run`（`orchestration/host_orch.py` + `next_levels/<program>/`）、`JitEntry`（源码 `@pl.jit`）、`DfxArtifact`（按 capability 识别各类产物）。后续换工程形态 = 加/改 recognizer，模型与下游不动。

**落点**：发现层是 **host 插件**（`tools/` 下新包，实现在 fork 的 `packages/`），对外一个 service + 向浏览器的投影。client 侧与 agent 的 run reference 从同一份模型取数，不允许 client 自行拼路径。

### 8. 证据能力词汇

五个 DFX 开关**完全正交、默认全关**（`docs/zh/dev/03-runtime-dfx.md` 开关映射表），故证据完整度非二值；仅标 `evidenceRole` 会误导（样例 `20260720` 有 swimlane / deps / CPM，但无 pmu、args_dump、scope_stats）。

模型存**问题类**而非文件清单：

| capability | 依据 | 能回答 |
|---|---|---|
| `irLowering` | `passes_dump/` ordered snapshots | 编译过程、Pass 前后 IR 差异 |
| `compileHints` | `report/perf_hints.log` | 编译期性能提示 |
| `memoryAllocation` | 内存分配报告 / `memory_map` 输入 | 内存分配与生命周期 |
| `timeline` | `chip_swimlane_records.json` → `merged_swimlane_*` | 泳道、任务时序、瓶颈 |
| `taskGraph` | `deps.json` | 运行时 DAG、依赖 |
| `criticalPath` | `CPM_*.json` / `critical_path_report.md` | 关键路径 |
| `hardwareCounters` | `pmu.csv` | 硬件计数器 |
| `tensorValues` | `args_dump/` | 精度分析 |
| `scopeStats` | `scope_stats/scope_stats.jsonl` | scope 级统计 |

`evidenceRole`（`compile-observed` / `runtime-observed`）保留为主轴摘要，但**不可单独作为判断依据**——它只说明有无 `dfx_outputs/`。该词汇同时接住"看板不止性能"：`tensorValues` 是精度线、`irLowering` 是编译线，与 `timeline` 平级，无天然的第一步。

**缺失项必须携带补救方法**。开关与产物一一对应，映射表本身即答案，且必须由工作台给出而非 agent 猜测（开关名是上游 literal，agent 编一个相近的会导致用户照敲失败）。示例措辞：

> 本次运行无泳道证据。下次运行加 `RunConfig.enable_chip_swimlane`（pytest：`--enable-chip-swimlane`）可采集。注意泳道采集会把 workload 跑两遍。

**区分两种"没有"**：

| 情况 | 判据 | 措辞 |
|---|---|---|
| 未开启 | `dfx_outputs/` 侧产物缺失 | 「本次未采集」+ 补救开关 |
| 运行未完成 | 是 run 目录但 compile 侧残缺（`passes_dump/` 空、无 `ptoas/` 或 `kernels/`） | 「运行未完成或失败」 |

严格说两者无法完全区分（DFX 产物亦可能因崩溃而缺），但"开关默认关"是压倒性常见情况；compile 侧产物本该无条件产出，缺失即异常。

**复跑能力单列**，不混入 `capabilities`（前者是"能做什么"，后者是"能回答什么"）：L2 `rerunFromDir` ← `compiled_meta.json`；L3 `rerunFromDir` ← `distributed_meta.json` 与完整子构建；`rerunFromScript` ← `debug/run.py`。而"有无源码可改"**不进 run 模型**——它是 (run, workspace) 对的属性，取决于会话 cwd，在知道会话上下文的渲染处推导。

卡片与看板上这些如何呈现（徽标、证据条、hover 展开）属内容层，随后续设计确定。
