# 工程基本规则

状态：2026-09-03 用户确认。细节按链接读取；本文件不复制内容治理与任务流程。

- R1 改造顺序：动态插件 spike → 静态插件（harness/packages）→ 最小内核改动。内核、slot、通信边界变更记录理由。
- R2 PyPTOUX 和官方镜像只读消费；不反向修改或默认同步。上游事实在对应版本的源码/官方文档复核。
- R3 新产品回路先验证再固化；文档治理无需为了形式创建运行时插件。
- R4 名称、主题和记录规则以 [content-routing.md](content-routing.md) 为准。
- R5 工程成果留现有代码区，研发过程进 work；AGENTS/.agents 是发现入口例外。根 README 不承载研发台账。
- R6 同一 checkout 单 writer，保留他人的未提交改动。不预设固定 Agent 分工；委派遵守当前用户及运行环境授权。交接前说明两仓状态，不自行提交或改历史。
- R7 接手从根 AGENTS 与 [研发导航](../README.md) 定位相关内容；任务恢复按 [task-workflow.md](task-workflow.md)。进入 harness 修改前还需读取其适用指令。
- R8 产品首版不自动判断 share-safe 或使用 PyPTOUX 数据等级作为 AI 准入门槛。用户主动选入/附加且 Host 可读取的数据默认可用于所请求的分析；这不是安全认证，不扩展到任意主机文件或执行权限。
- R9 保留上游 literal；区分真实采集、推导与示意，不伪造来源、运行成功、可比性或性能收益。PyPTO L2/L3 运行层级不是数据安全级别。
- R10 提交、推送、外部同步与公开发布按具体授权执行。历史 demo 发布目标不自动成为本产品发行目标；当前产品发行边界见 [distribution.md](distribution.md)。
- R11 版本控制不等于发布。发行物使用明确包含范围；不带入 work、开发 Agent Skill、凭据、个人配置或原始样例。不将“允许 AI 分析”解释为“允许公开发布”。
- R12 当前规则、主题设计、历史记录和执行状态各有唯一位置。旧根 notes 全量归档，新过程记录不再写入根 notes/prompts。
- R13 结构性决定记录日期、来源、状态、影响和替代关系。用户确认设计与实际实现、测试通过分开表达。

## 旧约定的替代

旧 R8/R11 中把数据真实性分级与 share-safe 门槛绑定的默认策略已按本次用户决定替代；真实性和发布授权边界保留。旧根 notes 及每次产物必须生成 Prompt 的约定由新的按需主题记录替代；不再限定记录者为固定 Agent 名单。

产品运行时六个 bundled Skills 尚未迁移这些策略，本次不改变它们的行为。差距与后续任务见 [官方 Skill 接入](../product/official-skill-integration/overview.md)。研发规范的生效不应被描述为运行时已经完成升级。
