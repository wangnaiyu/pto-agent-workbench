# 任务包与交接

状态：2026-09-03 已确认。只规范研发任务，不是工作台产品 Session 的数据模型。

2026-09-03 补充决定：按用户在本次对话中的两项确认，将原“关键子任务完成时更新”明确为每个可独立验收子任务的开始/完成 checkpoint。状态：accepted；适用于后续任务执行，不追改已归档记录，也不扩大任何任务的授权范围。

## 什么时候建立任务包

预计跨 Session、跨主题/目录，或需要多个验证阶段、明确依赖与交接时，在 work/inbox/tasks/YYYY-MM-DD-slug 建包。普通问答、单行修复不强制建包；Inbox 的散材料也不需要自动转为任务。

一个主题可以有多次任务，一个任务可关联多个主题。任务有可验收的终点；新增无关需求不无限追加进旧包。

## 最小文件与职责

| 文件 | 内容 |
| --- | --- |
| README.md | 目标、范围、非目标、授权、关联主题、执行者、读取顺序 |
| plan.md | 阶段顺序、交付物、依赖与完成标准；不重复维护实际进度 |
| status.md | 唯一当前进度：状态、步骤、更新时间、checkpoint、下一动作、阻塞、验证与未提交改动 |
| prompts/resume.md | 稳定的恢复指令，读取状态，不写死当前阶段 |
| final-report.md | 结束时说明结果、证据、未完成/延期项、正式产物位置和后续范围 |

按需增加 steps、notes、materials、evidence、open-questions。scratch 用于可重建中间文件，默认忽略入 Git；恢复任务所需的唯一证据不能只在那里。

## 状态与权限

task-status 使用 planned、active、paused、blocked、completed、cancelled。状态只记录事实，不启动自动化、不授予权限。planned 任务应写明何时可以执行；设计确认不等于功能实现、提交或发布授权。

status 至少包含 current-step、updated、authorization、checkpoint、next-action、blockers、verification、working-tree。记录外层与 harness 两个版本基线；有未提交改动时说明归属和文件范围，不把一次旧 clean 检查当作永久事实。

下一动作应具体、有限，并带可识别的完成条件。blocked 说明阻塞原因、已做的安全检查、解除方式；取消可以归档，但不能标 completed。不得以预算/时间不足把未完成标完成。

## 子任务执行与 checkpoint（逐项必做）

这里的子任务指 plan.md 中可独立验收的工作项，不是每次工具调用、每个文件修改或每个小编辑。每项都必须完成以下开始/完成记录，不能由 Agent 自行挑选“关键项”才记录。

### 开始前

确认前置依赖、完成标准和授权范围；尚未获得执行授权时不得启动。执行前先将当前子任务、准备执行的具体动作和预期产物写入 status.md，更新 current-step、next-action 和 updated，并保留最近已验证的完成点。整个任务开始执行时按实际情况更新 task-status，不把开始记录当作已完成证据。

长时间或有副作用的操作启动后，在取得可查询的真实执行标识时及时保存，并记录查询方式、输出/日志位置和已知状态。标识若仅在当前会话有效，应说明限制；无法取得或结果未知时如实记录，不编造 handle，也不保证进程一定能跨会话恢复。必要明细可放包内步骤/证据文件，status 保留链接；唯一恢复证据不能只放 scratch。

### 完成后、进入下一项前

1. 对照该项完成标准验收，执行与风险相称的检查，区分通过、失败和未验证；未达到完成标准时保留未完成状态。
2. 更新 status.md：完成的子任务、验收结果、产物/证据位置、遗留问题、未提交改动及下一项具体动作。只完成一个子任务不把整个任务包标 completed。
3. 将本项形成的长期有效设计、规则或结论及时回写正式位置；必要时更新主题记录/导航。没有相关变化时无需制造文档。
4. 上述验证、状态落盘和必要回写完成后，才可进入下一项。下一项仍须经过开始前检查；已有授权且条件满足时可连续执行，遇到明确确认节点、新权限或范围变化时停下说明。

status 是唯一当前进度来源；不在 plan、README 或 resume 中维护第二份进度表。也不因完成子任务自动 commit、push、归档任务或生成逐项 final-report。该协议约束 Agent 的执行顺序，不是自动唤醒/调度器。

## 中断恢复与其他 checkpoint

1. 从外层仓库进入，读根 AGENTS；按需读项目 Skill 与规范。
2. 读指定包 README、status、plan，再读当前步骤相关主题与代码约定。
3. 检查两个 Git 工作树、真实产物和权限；有冲突不覆盖别人的工作。结合已记录的执行标识、日志和输出检查先前操作/执行者是否仍在运行，不因会话中断就重复启动。
4. 对照状态和实际结果确定恢复点：已修改未验证则从验证继续；实际完成但未记账则验证后补记；结果未知先核查，不盲目重跑有副作用的动作。无法安全确定时记录阻塞并说明所需信息。
5. 修正 checkpoint，简述当前阶段、已确认与未验证内容，再按上面的逐项协议和已有授权继续；缺少材料先做可行检查，超范围动作需用户决定。

除每个子任务的开始/完成 checkpoint 外，重要决定改变、计划确认、关键验证完成、出现阻塞、用户要求交接时也更新 checkpoint。不依赖“Session 结束前”这个不可可靠检测的时点。正文方案及时回写，状态不依赖聊天记忆或本地临时路径。

## 结束与归档

按完成标准验收，写 final-report；把需要长期维护的规则、方案、脚本和遗留问题路由到正式位置。确认没有遗漏后，整包移至 work/archive/tasks/<原ID>，保留必要输入和精选验证证据，不保留另一份活动副本。

更新 work/README 与关联主题入口、相对链接。归档包是历史，默认不继续执行其中的 resume。用户重启旧任务时建立新任务包并引用旧结果；要沿用原包须先明确恢复范围和状态。

后续任务包可以在本包结束时建立，但是否执行以其自身授权为准。Git 提交、推送、上游更新和公开发布分别处理，不由归档动作隐含授权。
