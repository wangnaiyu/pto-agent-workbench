# decision-2026-08-25

## 新会话输入框 `+` 的草稿能力目录

> 本分区 `owner: Codex`、`source: user`、`status: accepted`、`decision: accepted`。

### 背景

输入框左下角的 `+` 需要在尚未创建 Session 的新会话草稿中展示可调用能力，同时继续遵守“首次发送才持久化”的既有约束：点击新会话入口、点击 `+`、打开菜单、搜索或选择条目，都不能分配 `sessionId`、恢复 Agent、执行能力或写入会话文件。

新会话有两种并列来源：

- Workspace 草稿：入口已经暂存 `workspaceId`、Host 可解析的可信 `cwd`，以及所选或默认 `agentPreset`。
- 未分组草稿：不传 `workspaceId`；最终工作目录只在首次发送时由 Host 解析，UI 使用 `default` 表达该状态。

未分组草稿不会随后自动变成 Workspace 草稿。两者只共享同一套目录协议和输入体验。

### DSH 机制复核

#### 插件不是能力目录分类

Cordis 插件是可挂载、可卸载的运行时扩展单元，可以提供 Service、Tool、命令、Skill provider、事件监听器、提示词、Host 逻辑、Client UI 和设置页。设置中的“插件列表”展示的是 Loader 树条目及其启停/Fiber 状态，不是用户可调用能力列表。

插件与 Skill 不是互斥的交付形式：

- 插件适合提供确定性、类型化、可校验的执行原语，以及面板、配置和生命周期能力。
- Skill 是按需加载的工作流指令与资源，适合让 Agent 理解目标、选择步骤并编排已有工具。
- 一个插件可以注册命令或 Skill provider；它最终贡献的命令/Skill 才进入草稿能力目录，插件本身不进入。

#### 当前 preset-scoped 命令

“Agent 命令”准确指当前所选 Agent preset 的 standing composition 新增或覆盖的命令，不是“所有会操作当前 Agent 的命令”。当前 DSH 随附 preset 的实际情况为：

| Agent preset | scoped 命令 |
|---|---|
| `standard` | `/plan`、`/compact` |
| `code` | `/plan`、`/compact` |
| `cordis` | `/plan`、`/compact` |
| `minimal` | 无 |
| 用户自定义 preset | 由其实际 composition 决定 |

`/compact` 是 preset 新增命令；`/plan` 在全局层已有同名定义，standard/code/cordis 的 scoped 定义绑定各自隔离的 plan-mode service，并覆盖全局 handler。两个 `/plan` 的公开名称、描述和参数可以完全相同，因此目录不能通过 descriptor 文本比较推断覆盖关系，必须由命令注册表提供真实 layer/origin。

### PTO 官方能力的两层结构

PTO 官方能力拆成插件与 bundled Skills 两层：

1. **PTO 插件原语**
   - Host tools/Service：运行产物解析、指标计算、before/after 对比、证据读取、数据分级与脱敏等确定性能力。
   - Client UI：泳道、计算图、内存、硬件结构、选区交互与结果卡片。
   - Settings：工具链路径、数据策略和显示配置。
   - Commands：打开面板、重置状态、导出结果等无需模型推理的确定性操作。
2. **PTO bundled Skills**
   - `pto-analyze`、`pto-debug`、`pto-optimize`、`pto-compare`、`pto-review` 等 Agent 业务工作流。
   - 源码位于本仓库 `skills/`，发布时由 PTO profile/launcher 装配为带明确 PTO origin 的 bundled provider。
   - Skill 正文负责编排 PTO 插件工具和 DSH 通用工具；底层数据契约、权限与强制规则仍由代码执行，不能只依赖指令提醒。

复杂的分析、诊断、调优和复盘属于 Skill；纯确定性操作才属于命令。平台迁移时优先保留 Skill 的业务流程和平台无关的数据/CLI 契约，为目标平台重写薄插件、MCP 或 UI 适配层。

### 产品术语与两部分目录

UI 只区分两种调用语义：

1. **Commands**：默认位于列表第一部分，UI 不显示该部分标题。
2. **Skills**：默认位于列表第二部分，显示 `Skills` 标题或明确视觉分隔。

“预设命令”不作为协议或产品术语，因为 Commands 同时包含 DSH、Agent、PTO 和第三方插件命令。“PTO 预设命令”统一称“PTO 官方命令”。

#### scope 与产品归属

Host 内部必须分开保存：

- `scope`：`global` 或 `agentPreset`，用于有效视图、覆盖与执行裁决，不直接展示。
- `origin`：用户可理解的产品归属，用于行尾标签。

Commands 的行尾来源标签为：

| origin | 标签 |
|---|---|
| DSH 第一方命令 | `DSH` |
| 当前非 PTO Agent preset 自己贡献的命令 | `Agent` |
| PTO 官方插件贡献的命令 | `PTO` |
| 第三方插件命令 | 插件友好名称；缺失时为 `Plugin` |

PTO 官方命令即使注册在 global scope，仍显示 `PTO`；Agent preset 只是引用 PTO 官方插件时不应把 PTO 所有权改写成 `Agent`。用户自定义 preset 自己新增或覆盖的普通命令显示 `Agent`。

Skills 的行尾来源标签为：

| origin | 标签 |
|---|---|
| 用户个人 Skill（`user-dsh` / `user-agents`） | `User` |
| PTO 官方 bundled Skill | `PTO` |
| 项目 Skill（`project-dsh` / `project-agents`） | Workspace 显示名称 |
| DSH 官方 bundled/provider Skill | `DSH` |
| 第三方插件 Skill | 插件友好名称；缺失时为 `Plugin` |

技术来源 `bundled` 不等于 PTO。未来 DSH 或第三方也可以发布 bundled Skills，因此 provider/发行 manifest 必须提供可信产品 origin；不能按目录名、Skill 前缀或任意 provider 字符串猜测。当前 PTO 工作台自己的 bundled root 只装配本仓库 `skills/` 时，其中条目统一标为 `PTO`。

`customSkillDirs` 是 profile 显式挂载的额外 Skill 文件系统根，不天然属于插件。用户配置的 custom root 默认归为 `User`；插件随包目录应优先由带 origin metadata 的 provider 注册。确需通过 custom root 装配插件内容时，配置必须同时声明 origin；缺失时降级为 `Plugin`。

### 已接受的范围矩阵

目录不得以 Host cwd 代替缺失的 Workspace。未分组查询 Skill 时传递真正的 `cwd: undefined`；文件系统 provider 因此不扫描 project roots，其他 provider 可以返回与 Workspace 无关的条目。

| 新会话来源 | DSH/PTO/第三方全局命令 | Agent 命令 | User/PTO/DSH/插件 Skills | Workspace Skills |
|---|---:|---:|---:|---:|
| Workspace 草稿 | 显示 | 显示，有则出现 | 显示，有则出现 | 显示，有则出现 |
| 未分组草稿 | 显示 | 不解析、不显示 | 允许显示；查询不得传 Host cwd | 不扫描、不显示 |

PTO 官方命令在两种草稿中都显示。首版所有用户可调用的 PTO 官方 Skills 也允许在两种草稿中显示；若某个 Skill 实际需要项目数据，由 Skill 在发送后的正式会话中提示用户选择项目或报告明确前置条件。当前不增加 `workspaceRequired` 元数据，等出现必须在菜单阶段隐藏的真实需求再设计。

用户个人 Skills 进入菜单。Skills 默认来源顺序为：

```text
User → PTO → Workspace → DSH → 第三方插件
```

每个来源内部按名称稳定排序。Commands 整体始终位于 Skills 之前。

### 用户体验决策

1. 点击输入框左下角 `+` 立即打开能力菜单，不再只向输入框机械插入 `/`。
2. 点击 `+` 与手动输入 `/` 使用同一份草稿能力目录、同一套搜索、排序、来源和冲突结果。
3. Commands 部分不显示标题；Skills 部分显示标题或明确分隔。空部分隐藏。
4. 每行四个元素位于同一行：最左是预留图标位，其后为名称，中间为描述，最右为来源标签。
5. 首版可以不展示实际图标，但所有行预留固定宽度图标位；协议保留受控的可选 `iconId`。不得允许任意 SVG、HTML 或远程 URL 直接进入渲染。
6. 名称保持可辨识；名称与描述之间保留明显间距。描述占弹性区域、单行截断并显示 `...`，hover/focus tooltip 展示完整描述。来源固定在最右并右对齐；过长 Workspace/插件名称同样截断，tooltip 与 accessible label 提供完整值。
7. 搜索匹配名称、描述和来源标签；搜索后仍保持 Commands 在 Skills 之前。
8. 选择条目只修改输入框，不执行能力、不创建 Session：
   - Command 按现有参数提示插入 `/name` 或 `/name `，保留图片接受能力、`input.hint` 和 claim 状态。
   - Skill 使用明确文本语法 `/skill name `，不再依赖与命令共用的 `/name `。
9. PTO 官方 Skills 默认同时允许用户和 Agent 调用，即 `userInvocable: true`、`modelInvocable: true`。特殊 Skill 才显式关闭其中一条调用路径。
10. 菜单底部显示弱提示：“选择后填入输入框，发送后才创建会话。”
11. 各来源独立加载和报错；一个来源失败不得移除其他已成功条目。错误至少隔离到 Commands 与 Skills，具备 provider 事实时进一步隔离到具体来源，并提供重试。
12. Workspace、Agent preset 或草稿 revision 变化时，立即关闭旧菜单、取消或忽略旧请求，并按新目标重新加载。
13. 菜单不展示绝对路径、内部 provider id、原始 scope key、完整 frontmatter 或任意 provider 对象。
14. 第一阶段不在无 Session 状态下打开依赖 Session 的命令弹窗。模型、权限等既有草稿安全控件继续由输入框工具栏负责。

### 名称冲突与发送语义

#### 同类冲突

- Agent scoped 命令覆盖同名全局命令，目录只展示最终 winner；winner 的产品 origin 决定行尾标签。
- Skill registry 继续按 scope、provider 和 rank 产生最终 winner；目录只展示该 winner 及其可信 origin，不展示被覆盖候选。
- 同一 registration layer 中重复命令仍由命令注册表拒绝，不为目录另造冲突规则。

#### 命令与 Skill 同名

同名 Command 与 Skill 都保留在各自部分。Command 仍使用 `/name`，Skill 使用显式 `/skill name`，因此两者不再依赖“命令优先、隐藏 Skill”的 UI 规避。

`/skill <name>` 是新目录生成和跨客户端共享的规范文本语法；Host 在首次发送的 pre-step 边界按正式 Skill 目录重新校验名称与调用策略，再注入完整 Skill。现有无冲突的 `/name` Skill 手势可以作为兼容语法保留，但新菜单不再生成它；发生命令同名时，裸 `/name` 仍解析为命令。

选择 Command 和 Skill 都只写输入框，但发送后的分派不同：

- Command 由命令管线执行 Host handler，不作为普通模型提示词。
- Skill 作为明确的 Skill 手势进入正式 prompt，在 pre-step 注入 Skill 正文后启动模型推理。

### 首次发送生命周期

首次发送是唯一的持久化边界：

1. 用户创建 Workspace 或未分组草稿，此时没有 Session。
2. 客户端请求草稿能力目录；查询只能读取注册表和 Skill 元数据。
3. 用户选择条目后，客户端只更新输入框文本。
4. 用户发送时，客户端按既有流程创建 Session，并应用草稿中的 Workspace、Agent preset、模型和权限等配置。
5. Host 使用正式 Session 的最终命令/Skill 目录重新校验名称、origin、调用策略与冲突结果。
6. 校验成功后再执行命令或注入 Skill；若能力已经消失、来源改变、用户/模型调用策略改变或冲突结果变化，则保留草稿文本并给出明确错误，不得静默降级为普通模型提示词。

打开菜单、过滤、重试、hover 和选择条目均不得触发第 4 步。

### Host 端设计

新增一个面向草稿的只读能力目录 seam：

```ts
composerCatalog.listDraft({
  workspaceId?: WorkspaceId
  agentPreset?: string
}): Promise<DraftComposerCatalog>
```

响应按两种用户调用语义建模，不再返回三个 UI 分区数组：

```ts
interface DraftComposerCatalog {
  revision: string
  commands: DraftCommandDescriptor[]
  skills: DraftSkillDescriptor[]
  partialErrors?: DraftCatalogError[]
}

interface DraftCatalogOrigin {
  kind: "dsh" | "agent" | "pto" | "workspace" | "plugin" | "user"
  label: string
}

interface DraftCommandDescriptor {
  name: string
  description: string
  input?: CommandInputDescriptor
  iconId?: string
  origin: DraftCatalogOrigin
}

interface DraftSkillDescriptor {
  name: string
  description: string
  modelInvocable: boolean
  iconId?: string
  origin: DraftCatalogOrigin
}

interface DraftCatalogError {
  area: "commands" | "skills"
  origin?: DraftCatalogOrigin
  code: string
  message: string
}
```

协议不接收客户端提供的原始 `cwd`。传入 `workspaceId` 时由 Host Workspace 注册表解析可信工作目录和显示名称；未传时 Skill lookup 使用 `cwd: undefined`，不得读取 Host cwd 的 project Skills。

#### 命令解析与 origin

- 保留无 Agent 的全局描述符查询和 standing-scope 有效视图查询。
- 命令注册表必须额外提供 layer/origin 事实，或直接返回 scope delta；不能用 descriptor 值比较判断覆盖。真实 DSH 的 scoped/global `/plan` descriptor 相同，是必测回归。
- Workspace 草稿解析选定 preset 的 standing scope；未分组草稿不解析 Agent standing scope。
- DSH/PTO/第三方插件 origin 来自可信 package/profile manifest 或注册元数据；不得按命令名前缀推断。
- 客户端不接收 handler、scope key、Fiber 或模块绝对路径。

#### Skills 解析与 origin

- Workspace 草稿用 Host 解析出的 `cwd` 与 preset standing scope 读取最终有效 Skill view。
- 未分组草稿以 `cwd: undefined` 查询最终非项目 view；文件系统 provider 不扫描 project roots，其他 provider 可以返回全局条目。
- 仅保留 `userInvocable: true` 的最终 winner；同时回传 `modelInvocable` 供 UI 标识与正式调用校验。
- preset 使用隔离 Skills service 时，必须通过不创建 Agent 的 standing-scope service 入口解析，不能退回根服务改变语义。
- Skill 的技术 `source`、provider identity 与产品 origin 分离。现有 Session `skill.list` wire 会移除 source/provider；草稿 seam 需要自己的最小 origin 投影。
- Workspace 标签来自 Host 注册表的显示名称，内部仍以 `workspaceId` 寻址；插件标签来自可信 display metadata，缺失时降级为 `Plugin`。

#### 图标、数据最小化与错误隔离

- 首版 item 可以没有 `iconId`；客户端仍预留图标位。
- 后续图标只允许受控图标 id 或由已安装 Client 插件注册的本地图标；不得传原始可执行/远程图形内容。
- Skill wire 不暴露绝对路径、完整 frontmatter、resource base、内部 provider 对象或原始 provider id。
- description 在 Host wire 上设置合理长度上限；UI 截断不代替协议边界。
- provider 瞬时失败尽量产生带 origin 的局部错误；不能让一个插件 Skill provider 清空 PTO、User 或 Workspace 的成功结果。
- 不存在或已删除的 `workspaceId` 返回明确目标失效错误；客户端关闭菜单并提示重新选择 Workspace。
- 目录查询不得调用 Session create/resume，不得产生 session header，不得写入 `~/.dsh*` 会话数据。

### 客户端设计

现有输入触发器以 `sessionId` 为唯一目标，扩展为 Session 与草稿并列的显式目标：

```ts
type InputTarget =
  | { kind: "session"; sessionId: string }
  | {
      kind: "draft"
      draftRevision: string
      workspaceId?: WorkspaceId
      agentPreset?: string
    }
```

实现要求：

- 新增统一草稿目录 source，将 `commands` 和 `skills` 投影到同一菜单；不要让 `ui-commands` 直接依赖 `ui-skill` 并在浏览器拼接两套远端 API。
- source 同时服务 `+` 点击与 `/` 输入触发，并拥有 `/skill <name>` 的 pick、lexicon 与发送时消歧语义。
- 现有 candidate 需要增加右侧 origin label 的正式字段；不得把 origin 塞进 description。
- row 组件实现固定图标位、名称、截断描述和右对齐来源；tooltip/focus 与 accessible label 暴露完整文本。
- Session 创建完成后，输入目标从 `draft` 原子切换为 `session`；正式 Session 目录也必须支持同样的两部分、origin 和 `/skill` 语法，避免发送前后体验漂移。
- 以 `draftRevision` 防止迟到响应污染新草稿；Workspace 或 Agent preset 切换必须产生新 revision。
- 各来源可以独立显示 loading/error/retry；成功来源不得被失败来源遮蔽。

### 缓存与失效

草稿目录可按 `{workspaceId?, agentPreset?, commandGeneration, skillGeneration, originGeneration}` 缓存，但缓存不能改变隔离规则。

以下事件必须使相关缓存失效：

- 命令注册表 `commands/change`。
- Skill provider 的 `skills/change` 或文件系统失效通知。
- Workspace 更新、删除、显示名称或路径变化。
- Agent preset 变化。
- PTO/DSH/plugin origin manifest 或 display metadata 变化。
- 草稿 revision 变化或草稿被丢弃。
- Host 重连、profile 重载或运行时 generation 变化。

如果现有底层事件未转发给浏览器，由草稿目录 seam 产生合并后的 revision 或失效事件，避免客户端监听 provider 细节。

### 包边界与改造优先级

按工程 R1：

1. 先用动态插件 spike 验证无 Session 读取全局命令、standing-scope 命令和指定 Workspace Skills。
2. 只对现有注册表补必要的只读 layer/origin/service 解析能力。
3. 协议适配、产品 origin、过滤、排序、错误隔离、缓存和 UI 留在静态 Host/Client 边缘 package。
4. PTO Host tools 放静态 Host 插件，面板和设置放 Client 插件，业务工作流放本仓库 `skills/` 并由 PTO bundled provider 装配。

动态 spike 已证明读取回路和 Session 不变基线可行，但它使用不同 description 模拟 scope 覆盖，尚未证明“descriptor 完全相同的 scoped `/plan`”可以分类。第二阶段必须先补真实 registration provenance，再固化最终 seam。

第二阶段已固化为 `harness/packages/host/composer-catalog`：它通过 `composerCatalog.listDraft` 读取命令注册表、正式 Skill registry、Workspace 注册表与 preset standing composition，并已装配进 Web Host bundle 和 Client Remote facade。命令注册增加不进入普通 descriptor 的 `provider` 技术身份与 `listDiscoveryForScope()` layer 事实；产品 origin 由 profile 可信 `providerOrigins` 映射决定，未知 provider 降级为 `Plugin`。响应使用内容哈希 revision 作为当前静态 generation；推送式失效留到客户端统一 source 阶段按真实缓存需求补充。

该静态 seam 已覆盖 identical-descriptor scoped winner、User/PTO/Workspace/DSH/plugin 排序、未分组 `cwd: undefined`、隔离 Skills service、局部 Skill/preset 错误、无效 Workspace 和真实 Loader/YAML 装配。它不实现菜单 UI、`/skill <name>` 解析或首次发送再校验，这些仍分别属于第四至第六阶段。

第三阶段已把 PTO 官方业务 Skill root 固定为工作台仓库的 `skills/bundled/`。PTO profile 将原本禁用的 Host `skill-filesystem` row 精确启用为独立 provider `pto-bundled`，设置 `includeDefaultRoots=false`，并以相对 patch `baseUrl` 解析该 root；因此它不扫描用户、Workspace 或 DSH 默认 roots。`composer-catalog.providerOrigins` 只把 `provider=pto-bundled + source=bundled` 显式映射为 `PTO`，其他 bundled provider 仍按自身可信 metadata 分类，缺失时保持 `DSH` 默认而不是继承 PTO。

首个基线 Skill 为 `pto-evidence-intake`，用于 PTO 诊断、调优或复盘前的数据等级、share-safe、证据角色和 claim 状态整理。其 frontmatter 省略 DSH 专有调用开关，使用 DSH 的默认 `userInvocable=true`、`modelInvocable=true`，从而同时兼容通用 Skill 校验并允许用户与 Agent 调用。

第四阶段已新增草稿专用 Client package `ui-composer-catalog`：它把 `composerCatalog.listDraft` 投影为一个统一 `/` source，由同一个显式 draft `InputTriggerController` 同时服务键入 `/` 和前置 `+`。菜单以无标题 Commands 在前、`Skills` 分区在后，行内预留图标位、限制描述为 80 字符并显式省略、保留完整 tooltip/accessibility 文本，最右显示可信 origin。搜索覆盖名称、描述和 origin；Command/Skill 同名仍分区保留。

草稿 target 现携带 Workspace 和已暂存 Agent preset；两者变化只会更换目录 identity 并关闭旧菜单，不清空驻留输入。请求按 target single-flight，Host 重连会清空缓存；来源失败保留可重试行，局部错误不隐藏成功项，显式重试只失效当前 source。选择项仍只作 span-CAS 文本插入：Command 为 `/<name> `，Skill 为规范 `/skill <name> `，不创建 Session。

第五阶段已把显式 Skill 手势收敛到 `dsh-tool-skill` 的 Host `agent/pre-step` 边界：任意 Client 只要在直接用户文本中发送以空白为界的 `/skill <name>`，Host 就按正式 Session 的 cwd、scope、实时 Skill definition 和 `userInvocable` 重新读取并注入正文。Session `ui-skill` 和草稿 `ui-composer-catalog` 都只生成该规范文本；输入装饰 lexicon 现支持带空格词形，会把完整 `/skill <name>` 作为一个范围高亮。旧 `/<name>` 仍可手输，但 Host 会查询当前 Agent 的有效命令 service，存在同名 Command 时不再将它解释为 Skill；`/skill` 本身保留为引导词。

第六阶段已把发送准入和正式 Session 菜单收敛到同一份 Host 事实：`composerCatalog.listSession({ sessionId })` 从已创建 Session 的实时 Agent scope（未 attach 时使用持久化 preset standing scope）、Workspace 归属与隔离 Skill registry 投影最终 Commands/Skills。该查询不恢复冷 Agent，也不启动 turn。Session 下的 `ui-commands` 和 `ui-skill` 优先消费这份目录，因而菜单同样使用无标题 Commands、`Skills` 分区、预留图标位和可信 origin 标签。

新会话首次发送会先实体化唯一 Session，然后在 prompt 持久化前拉取 `listSession` 对比草稿目录快照。已发现能力消失、origin 改变、Skill 调用策略改变，或新出现的同名 Command/Skill 冲突均拒绝发送；捕获的文本和附件保留在当前可见的真实 Session 输入框，且不产生模型 prompt。对没有既往菜单快照的纯手输文本，系统仍以文本为真值：用最终目录校验规范 Skill 是否存在且可用，但无法比较一个从未被观测的历史 origin。

此外，公开 `session.prompt` 边界会对所有 Client（包括 CLI/ACP 手输）再独立解析规范 `/skill <name>`，按精确 Session registry 与 `userInvocable` 策略做持久化前准入。目录不可用返回 `skill-catalog-unavailable`，名称消失或已禁止用户调用返回 `skill-unavailable`；两者都不会落账用户消息。pre-step 仍只负责正文加载和注入。

第七阶段的首个纵向切片选择“运行产物准入”，因为分析、调试、调优、before/after 和复盘都依赖同一份 run 识别与 evidence capability 事实。PTO profile 新增静态 Host package `@deepseek-ai/dsh-tool-pto-run`：

- `pto_run_discover` 只扫描当前 Session workspace，按顶层 `kernel_config.py` 识别 PyPTO 3.0 L2 run，按 `orchestration/host_orch.py` 识别 L3 run；目录名、`_jit_` 和时间戳都不参与识别。
- 扫描按需执行、有限深度，剪枝 `.git`、`node_modules`、`__pycache__` 和 `3rdparty`；识别出 run 后停止下探，`next_levels` 子构建不炸成独立条目。
- `pto_run_inspect` 在 workspace containment 内检查 evidence / rerun capabilities，只报告 `available`、`not-observed` 或 `unknown`，不读取 raw 内容、不推断因果；路径仍是可追溯 opaque evidence，run identity 固定为 `unverified`。
- `compiled_meta.json` 和 `debug/run.py` 只决定对应复跑能力；缺失不否定 run。`fullRecompile` 依赖 `(run, workspace, environment)`，run 单体检查始终保持 `unknown`。

同一切片新增 PTO bundled Skill `pto-analyze`。它先调用上述原语建立 run 和 evidence health，再按 `timeline` 性能、`tensorValues` 精度、`irLowering` 编译三类问题路由通用文件读取；证据不足时只返回缺口与补采方向。该 Skill 默认只读，不能自行改代码、改产物或触发复跑；数据等级、share-safe 和 claim verification 不明确时先组合 `pto-evidence-intake`。

第七阶段第二个切片新增 `pto-debug`，并补齐同一 Host 原语中原本不应交给模型猜测的调试事实：五类可选 DFX capability 均携带准确 `RunConfig` / pytest 补采 literal，泳道补采额外标记 workload 会运行两遍；`runHealth` 将 compile 侧关键产物状态与可选 DFX 缺失分开。完整 L2 清单若在 `passes_dump/`、`ptoas/` 与 `kernels/` 下均未观察到文件，返回 `incomplete-or-failed`；清单截断或 L3 父 run 返回 `unknown`，L3 必须继续检查相关 `next_levels` 子构建。

`pto-debug` 负责保留用户 symptom、定位首个有证据的失败阶段、区分 observed fact / candidate cause / hypothesis，并给出最小判别动作。它把 DFX `not-observed` 优先表达为“本次未采集”，把上述 compile-side 状态表达为“运行未完成或失败”，但仍保留 DFX 也可能因执行中断而缺失的异常解释。该 Skill 默认只读，不执行 `debug/run.py`、pytest、编译或设备 workload；需要执行或修改时必须先返回动作、预期证据、风险/采集成本并取得另行授权。

第七阶段第三个切片新增 `pto-optimize`。它不充当自动改码器，而是把 `pto-analyze` / `pto-debug` 中已有证据支持的瓶颈或失败机制转成有界候选实验：每个候选必须带可修改 source/config anchor、单一材料变量或显式绑定的变更集、作用机制、预期方向、风险、falsifier、正确性与性能验收条件、停止条件及回滚。没有可靠 source/config join 时只能给 conceptual action 与身份缺口，不能因名称、路径或时间接近就把当前源码绑定到 baseline。

本切片同时明确真实实验前的三对象边界：baseline run 是不可改的证据；source workspace 是取得授权后才可修改的源对象；environment 是决定复跑可行性和比较口径的独立身份维度。candidate 必须来自可恢复的源码工作副本并写入新 output directory，diagnostic run 只因多采 DFX 不会自动成为 candidate。Before/After 只有在 task、workload/input/shape、hardware/environment、metric scope/aggregation 与采集开销兼容时才允许作因果比较；阈值缺失时标 `needs-user-confirmation`，不能由 Agent 编造。

当前 `pto-optimize` 是 proposal-only：不改源码、配置或生成物，不执行 replay、pytest、编译、设备 workload 或 DFX 补采。这个边界使候选建议可以先被用户审阅，并把可恢复 working copy、新目录写入、实验事务、比较计算留给后续有确定性执行约束的切片；因此本轮无需新增 Host 原语。

第七阶段第四个切片新增 `pto-compare`。它要求 baseline/candidate role 显式指定，不从目录名、时间戳或顺序推断；两边都先经过 `pto_run_inspect`。最小 comparison identity 包含 operator/program（L3 还含 rank/dispatch）、workload/input/shape/dtype、hardware、software/compiler/runtime、collection config/overhead、metric definition/unit、scope/timebase、round/warmup/samples/statistics，以及 source/build lineage 与唯一声明的 candidate change。

task match 使用 `matched / partial / unmatched / unavailable`，不使用未经校准的 confidence 百分比。只有 task=`matched`、所有 identity 维度有证据且兼容、唯一材料差异为已声明 candidate change 时，才允许显示 collected delta；其余状态只并列展示两边观察、列出 mismatch，不计算 combined delta，也不判断优化假设。不同 DFX 开销、scope、timebase、aggregation、hardware、workload 或未声明源码/config 变化均构成 confounder。

比较值区分 `projected / simulated / collected`。projection 不是复跑验证；simulated 只能支持 L2 fixture 的确定性规则，不能证明真实硬件收益。admitted metric 使用 `candidate - baseline` 的 absolute delta，baseline 非零时才计算 relative delta；没有预设 threshold 与 variance/repetition 规则时只报告方向，significance 保持 `needs-user-confirmation`。结果词汇限定为 `supported / not-supported / inconclusive / incomparable`，正确性、编译、运行、内存或可移植性 hard guard 失败优先于性能改善。

本切片仍不新增 comparison Host 原语。当前原生 run 没有 canonical comparison manifest，检查工具也明确返回 `identityStatus=unverified`；一个只比较模型填入的 identity 字符串与数字的通用工具不能验证证据真实性，反而会伪造系统级保证。待 app-owned run registry 和具体 metric adapter 能从源 artifact 建立 comparison identity 后，再把 gate、统计与 delta 下沉到代码。本轮 Skill 使用现有只读文件/计算能力并把 arithmetic 标为 derived。

第七阶段第五个切片新增 `pto-review`，完成当前已命名业务 Skill 链。它收集 `pto-evidence-intake`、analysis/debug、candidate、authorization/execution 和 comparison 的已有输出，形成 claim–evidence–decision ledger；缺失阶段保持缺失，不为了叙事完整而补写。每条 material claim 保留类型、scope、来源路径、冲突/替代解释、`verified / conflict / stale / unverifiable-missing / unverifiable-empirical / needs-user-confirmation` 状态及其 decision consumer。

复盘必须把 projection、simulation 与 collected validation 分层，并沿用 `pto-compare` 的 `supported / not-supported / inconclusive / incomparable` 语义。成功 candidate 不会反向证明原机制，Agent recommendation 不会自动升级为用户授权；没有已知 decision owner 或正式决定时 disposition 为 `no-decision`。负向、中性、失败和不可比结果都保留，并记录可复用边界：product line、source/build lineage、hardware、software/runtime、workload/shape/dtype、metric scope、collection config 与已知限制。

`pto-review` 输出是带源引用的 derived record，不是 app-owned experiment registry、事实源、merge/deploy approval 或发布许可。本切片不新增 review Host 原语；在持久化 schema 与 registry 尚未设计时，把 Markdown 汇总写入工具状态会混淆记录与事实。Skill 默认只返回复盘，只有用户明确要求时才写文件，并且不改源代码、产物或触发复跑。

五个业务 Skill 的联合复核保留现有命名。`pto-analyze` 与 `pto-debug` 的边界按用户问题而不是 artifact 类型划分：前者回答“运行产物显示了什么”，后者回答“显式失败/错误结果为何发生，以及哪个只读检查能区分候选原因”。因此数值与 compiler artifact 可以进入两者，但 characterization 与 failure localization 的职责、触发描述和交接必须分开。`pto-optimize` 保留易发现的动词名称，但其产品契约仍是 proposal-only；Skill 名称不得被解释为已改码或已执行。

复核同时确认，当前五个命名 Skill 只闭合认知与决策链，不闭合操作链。`pto-optimize` 与 `pto-compare` 之间缺少获授权后的 experiment transaction：它至少要以 app-owned 身份绑定 immutable baseline、recoverable source workspace、environment、declared change、new output directory、stop/rollback、actual run 与 authorization receipt。下一切片先定义并 spike 这份 experiment contract/registry，再在其上实现真实执行编排；metric adapter 与 comparison Host 原语随后消费非 caller-supplied identity，evidence-gated UI 最后消费同一 registry/capability 事实。不能先做 UI，也不能把通用 bash transcript 当成 experiment registry。

experiment contract/registry 动态 spike 已验证可行的数据形态：一个 experiment 使用 Host 生成 id、整记录原子 revision 与 append-only event ledger，状态限定为 `planned → authorized → running → completed|failed|cancelled`。记录绑定 Session Workspace、recognized baseline、source workspace、source/environment identity、declared change、candidate output、stop/rollback、authorization receipt 与 actual run。每次迁移要求 `expectedRevision`；terminal record 不再迁移；同一 candidate output 只能归属一条记录。模型可见能力只包含 `pto_experiment_plan / get / list`，不包含 authorize、begin、complete、fail 或 cancel。

spike 使用真实 DSH domain data form 和 JSON backend，已证明动态插件停止/重启后记录与 ledger 可恢复，且其他 Workspace 不能通过模型工具读取。但动态插件的 `harness.handle` 可由该插件自己的 browser half 调用，不能证明 identity 来自可信 adapter、authorization 来自用户消息、transition 来自 executor；因此 spike 中这些事件显式标为 `spike-simulated`，不能直接固化为生产授权链。正式静态 Host package 必须从可信 Session/user-message seam 生成 receipt，并只向 executor 开放执行迁移。

PyPTO 3.0 当前源码还确认 `ir.compile()` 对显式 `output_dir` 使用 `os.makedirs(..., exist_ok=True)`；所以 planning 时的 `absent-observed` 不是目录锁。正式 executor 必须在开始事务时原子占用 candidate output，并处理检查—创建竞争，不能只依赖 registry 的旧观察。动态 spike 为闭环最小复写 marker recognizer；静态实现必须复用 PTO run package 的 inspection 契约，不维护第二套 run 识别规则。

静态固化已落在 Host package `@deepseek-ai/dsh-pto-experiments`。它拥有 `ctx.ptoExperiments` 与 zod 校验的 `pto_experiments` domain，只向模型开放 `pto_experiment_plan / get / list`；proposal 使用 Host id、`revision=0` 与 `planned` ledger，按 opaque filesystem target identity 隔离 Workspace，并把 candidate 所有权检查与持久 put 串行化。baseline 准入复用 `tool-pto-run` 新导出的 `recognizePtoRun()`，不再复制 marker 逻辑；JSON backend 重启后可恢复同一记录。

本轮对可信边界的复核没有把 spike 模拟能力带入生产。planning 切片当时的 `ctx.approval.request()` 只返回 outcome，`ctx.fs` 也没有通用的独占目录创建 operation，因此静态 planning 只存 `absent-observed`。这个约束促使真实 executor 必须把 experiment-bound receipt、可信 identity adapter、candidate output 原子 reservation 与 executor-only revision transition 作为同一执行准入闭环交付。

第七阶段后续真实 executor 切片已完成这一闭环：

- approval seam 新增 `requestDecision()`，只在 `approval/asked` 与 `approval/decided` 都 commit 后返回 service-issued id 与 closed outcome；旧 `request()` 保持兼容。
- filesystem seam 新增 `reserveDirectory()`：parent 必须已存在，final entry 必须不存在，并发只有一个 winner，且 sandbox/local/E2B 共用同一 contract。
- `PtoExperimentStore.execute()` 是唯一可信 Host transition API，不注册为模型工具，也不提供可拆分的 bind/authorize/begin/complete 入口。
- 准入要求审批 Agent Session 与 experiment 同 Workspace，使用固定 argv 绑定 clean Git `HEAD` 和已配置 Python/PyPTO environment，将精确 revision、identity、candidate、command/timeout、declared change、stop/rollback 与 `danger-full-access` 明示给用户。
- `allowed-once` 后再次检查 identity/path/baseline/candidate，原子占用 candidate，把 receipt、identity、reservation 与 `running` 一次持久后才运行存储的 command。Host 注入精确 `DSH_PTO_EXPERIMENT_OUTPUT_DIR`，不持久 stdout/stderr 内容；exit zero 仍必须通过共享 PTO run recognizer 才 completed。
- Host 重启时无法重新 attach 前台 child，因此遗留 `running` fail closed 为 failed。reservation 成功而随后 storage put 失败时可留下空 orphan directory，但 workload 不会开始，path 也不可静默复用。

这一切片闭合了一次真实 experiment 的执行事务，但尚不闭合可比较证据。

第七阶段后续 metric/comparison 切片现已闭合首个 app-owned collected 比较回路：

- `PtoExperimentStore.execute()` 在 recognized L2 candidate 完成后，只从精确 registered run 的当前 `dfx_outputs/chip_swimlane_records.json` 与 `compiled_meta.json` 采集。路径 containment 与文件大小受应用约束；固定 Python probe 复用 PyPTO 官方 `simpler_setup.tools.swimlane_converter.read_perf_data()`，不复制 cycle/join 公式。
- 首个版本化 adapter 是 `pypto-chip-swimlane-makespan-v1`：metric 定义为 `device-dispatch-makespan`，单位微秒，取最晚 finish 减最早 dispatch；scope 为单次 L2 run。持久记录同时绑定 metric definition、compiled task contract/task topology、hardware topology、artifact digest、source/environment/command lineage。
- 指标不可用不会改写已成功的 run：缺失为 `not-observed`，格式错误或超界/超限为 `invalid`。首版不猜测 legacy `l2_swimlane_records.json` 或 L3 dispatch tree。
- 新增 `compare()` Host API 与 `pto_experiment_compare` 模型工具。baseline 必须是同一 Workspace 中另一条 completed experiment 的 registered actual run；metric/task/hardware/environment/command/source-root/exact committed Git diff 七个 identity 维度全部可用且匹配时才计算 combined delta，否则返回 `incomparable` 且不给 delta。
- admitted delta 使用 `candidate - baseline`，baseline 非零时才给 relative delta，并报告 improved/regressed/unchanged 方向。因尚无用户所有的 threshold、repetition 或 significance rule，result 固定为 `inconclusive`，不会自动声称 `supported / not-supported`。comparison 是对持久观测的按需派生，不是新 lifecycle transition。

至此，前一切片所缺的非 caller-supplied metric identity/collection 与 comparison Host 原语已完成。第七阶段的下一个主线切片是 evidence-gated details/overlay/comparison UI，只消费同一 registry/capability 事实；L3/legacy adapter、多次采样和 threshold/significance policy 保持显式延后。

这些切片刻意不增加 `/analyze`、`/debug`、`/optimize`、`/compare` 或 `/review` 命令：分析、诊断、候选实验设计、证据解释与复盘需要模型推理，属于 Skill。它们也不提前建设 Client 看板；后续 UI 必须消费同一能力契约，并按 evidence gate 选择 renderer，而不是重新扫描目录或默认渲染泳道。

### 不采用的方案

- **为目录查询临时创建 Session**：违反首次发送才持久化，也会制造空会话和磁盘数据。
- **客户端硬编码命令或 origin**：无法反映 profile、插件、preset 和运行时变化。
- **客户端扫描 `.agents/commands`**：DSH 没有该官方命令格式。
- **客户端分别调用 Session command/skill API 再合并**：草稿没有 `sessionId`，且会复制 Host 的 scope、origin 和冲突语义。
- **用 descriptor 文本差异判断命令覆盖**：真实 scoped/global `/plan` 的公开 descriptor 可以相同。
- **按 Skill/命令名称前缀推断 PTO/DSH/plugin origin**：名称不是可信所有权。
- **把所有 `bundled` 都标为 PTO**：技术来源不能区分未来 DSH、PTO 与第三方随包内容。
- **未分组按 Host cwd 加载项目 Skills**：会把安装目录或启动目录误认成用户 Workspace。
- **命令与 Skill 同名时隐藏 Skill**：新设计保留两者，并以 `/skill <name>` 显式消歧。
- **选择菜单项时立即执行**：命令与 Skill 都必须等首次发送。
- **用 Skill 替代可执行工具、数据规则或 UI**：指令不能提供确定性执行与强制边界。
- **把复杂 Agent 分析工作流包装成直接命令**：会混淆语义并增加平台迁移成本。

### Evidence-gated comparison UI 边界

首个 UI 切片采用“业务行 + keyed details”边界，而不先建全局 overlay。`ui-tool` 继续独占 `conversation.details.tool` 这个整面板 single slot，并新增 session-scoped keyed 子槽 `tool.result.detailview`，按已选 call 的 wire tool name 分派 details 输出体；没有注册的工具继续走现有结构化卡片或 raw text fallback。这样业务插件不需要接管所有工具，也不建立第二份 Session/registry 状态。

PTO profile 新增纯 Client package `@deepseek-ai/dsh-client-ui-pto-experiments`，只认领 `pto_experiment_compare` 的 transcript row 与 details。它只解析已冻结、已持久化的 Tool result JSON，不重新调用 Host、不读取 artifact，也不自行查询 experiment registry。UI 只接受闭合 comparison schema：`inconclusive` 必须同时具备两个 app-owned collected metrics、七个 `matched` identity、非空 baseline experiment，以及与两边数值一致的 absolute/relative/direction delta；任一结构或算术不一致都降级为“依据不可用”。`incomparable` 必须保持 `delta: null`，只并列展示 metric、identity 与 reasons。

UI 不把 `improved` 方向升级为 supported/success，也不产生新的 comparison 事实；`needs-user-confirmation` 始终可见。running、Tool error 与 malformed success 分别显示等待、失败和依据不可用，且后两者不显示数字差值。

全局 `shell.overlay` 暂不启用：当前 durable result 已足以闭合行→选中 call→details 的最小阅读路径。待出现跨 call 聚合、实验列表或主动打开 dashboard 的真实需求后，再基于 registry projection 设计独立 overlay controller；不能复用单次 Tool 输出拼接全局状态。

## PTO 持久实验 Dashboard 切片

### 需求验证与界面选择

跨 experiment/call 的 dashboard 需求成立。实验记录由 `pto_experiments` domain 持久化，Host 重启后仍存在，且 planned/failed/completed 记录不保证都能从当前 transcript 重建；因此 transcript JSON 不能作为列表事实源。此前只有模型工具 `pto_experiment_list` 能读取这些记录，用户缺少主动查看和刷新入口。

本切片不采用 `shell.overlay`。该 slot 是 root-scoped、默认 click-through 的全局浮层；若承载 Session 实验列表，还需要额外的当前 Session controller，并可能遮挡后续执行审批。现有 `conversation.view` 已提供 session-scoped 生命周期、tab 切换与 composer 共存语义，适合持久工作台页面。PTO profile 因而形成 `Chat(order=0) → Trajectory(order=10) → Experiments(order=20)` 的会话视图环；没有新增 UI slot。

### 动态 spike 结论

`experiments/pto-experiment-dashboard-spike` 先验证两条 Host handler：

- `list` 只接受 `sessionId` 与 bounded limit，由 Host 从已有 Session header 解析 cwd，再调用 experiment registry；未知 Session 失败，读取前后 Session 数量与 live Agent 集合不变。
- 为后续预演的 `execute` 必须从同一个 `sessionId` 取得 live Agent，并把 Session cwd、该 Agent 与 optimistic revision 交给 registry；冷 Session 不允许执行。

wire 投影只包含展示字段，不含 `workspaceKey`、`targetKey`、scope key 或 Agent 对象。spike 证明 session-addressed authority/data contract 可行，但执行 handler 不进入本切片的生产 Remote。

### 固化边界

- 新增 Host edge package `@deepseek-ai/dsh-host-pto-experiment-dashboard`，提供只读 `ptoExperimentDashboard.listSession({ sessionId, limit? })`。这是新的跨 Host/Client communication seam，故在本决策中明确登记。
- Client 不能传 cwd/path；gateway 只读权威 Session 和 `ctx.ptoExperiments`，返回 newest-first、最多 100 条的最小投影。默认 UI 请求 20 条；内部 filesystem/storage identity 不出 Host。
- `@deepseek-ai/dsh-client-ui-pto-experiments` 新增 **Experiments** conversation view。进入视图时读取一次，用户可显式刷新；loading、empty、Remote error 和 truncated 状态在视图内隔离。
- Web bundle 携带但默认禁用 registry、dashboard gateway 与 PTO UI；PTO profile 同时启用三者。generic DSH profile 不获得 PTO 产品行为。
- dashboard 读取不创建/恢复 Agent、Session 或 turn，也不进入模型上下文。comparison row/details 继续只消费冻结 Tool result。

### 明确延期

本切片不提供实验执行按钮、自动轮询、push invalidation 或全局 overlay。下一切片必须先定义用户触发执行时的长 Remote 生命周期、审批交互、并发/optimistic revision、unmount 与完成后刷新策略；不能直接把动态 spike 的 execute handler 当成生产权限边界。

## PTO Dashboard 用户执行切片

下一切片已经闭合用户从 **Experiments** 页主动执行一次已规划实验的最小回路，且没有扩大模型权限：

- `ptoExperimentDashboard.executeSession({ sessionId, experimentId, expectedRevision })` 是长 Remote。Gateway 从已有 Session 取得 cwd 与 live Agent，把 UI 当前看到的 optimistic revision 原样保留；浏览器不能提供 path、Agent、identity、command 或 authorization。
- approval service 的 audit pair 必须 turn-enclosed，idle Agent 上直接调用 executor 会被正确拒绝。Gateway 因而向同一 Agent 投递一条私有 plugin follow-up；Agent loop 打开正常 turn 后，Gateway 在 `agent/pre-step` 中识别该 message id，调用 `PtoExperimentStore.execute()` 并返回 `reject`。私有消息被 inbox claim 后不会追加为模型可见 `user/message`，也不会创建 `step/start` 或触发 LLM；turn 只承载审批审计与 non-model Host operation。
- `PtoExperimentStore.execute()` 仍是唯一准入与状态迁移 owner。既有 approval surface 展示精确风险信息并收集一次性决定；Dashboard 不实现第二套确认框，也不把按钮点击当作授权。
- Gateway 为每个 experiment 持有一个临时 cancellation controller。同一 experiment 的并发启动在 controller 层失败关闭，registry 的 active-executor 与 revision 检查继续作为第二层防线。
- 视图 unmount/tab 切换只丢弃 Client observer，不发送 abort。重新挂载后，`listSession` 会在持久记录上叠加 `active/cancellable` 临时状态；只有原发起 Session 可以调用 `cancelSession()`。
- `cancelSession()` 中止 Host execution signal，并等待长执行调用结算后才返回。已经进入 durable `running` 后，terminal settlement 显式移除 workload signal：取消只能终止命令，不能阻止 registry 写入 `cancelled`。执行或取消结算后 Client 重新读取权威 registry；没有通过本地预测改写 durable status。
- planned 行才显示执行动作。活动期间显示“等待审批或执行中”；action/Remote error 隔离在对应 Dashboard 行，不进入 transcript 或模型上下文。

这一设计不把长执行包装成模型 step，但会使用一个正常、blocked 的 non-model turn 满足 approval audit 的 durable boundary；这是 approval contract 所要求的最小 Session 生命周期，不是模型提示或第二份业务状态。暂不引入 `ctx.jobs`、自动轮询、push invalidation 或全局 overlay。Gateway controller 是 Host 生命周期内的临时编排状态，不是新的事实源；Host 停止时会 abort 并等待活动执行结算，已有 registry restart recovery 继续处理异常遗留的 durable `running`。

真实 PTO profile 的应用内浏览器 QA 已覆盖两条链路：`planned → approval → completed@4`，以及 `planned → approval → running@3 → Experiments unmount/remount → cancel → cancelled@4`。重挂载从 Host 重新读到 active/cancellable；完成记录显示 app-owned metric `not-observed`，取消记录显示 durable failure reason。QA 同时确认临时 source Git worktree 保持 clean，审批 receipt、execution ledger 与 candidate marker 均按 registry 契约落盘。
